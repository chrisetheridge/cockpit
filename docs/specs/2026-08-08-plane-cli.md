# Plane CLI Spec

## Goal

Create a TypeScript command-line client for Plane that treats software agents as the primary user while providing a polished, keyboard-driven TUI for humans. The same application capabilities must be available through deterministic commands; the TUI is a presentation layer, not a separate product surface.

## Requirements

### Confirmed

- Use TypeScript and support Node.js 22 or newer.
- Authenticate to Plane Cloud and self-hosted Plane with a Personal Access Token.
- Running `plane` with no arguments in an interactive terminal opens the TUI.
- Running commands, piping output, or using a non-interactive terminal never opens the TUI.
- Support normal operations exposed by Plane's public, PAT-authenticated API.
- Use `/work-items/` terminology and endpoints; do not expose deprecated `/issues/` commands.
- Make machine-readable output, errors, discovery, pagination, and non-interactive safety first-class contracts.
- Provide a reusable agent skill alongside the CLI.
- Every TUI operation must have a command equivalent.
- Support Plane Cloud and configurable self-hosted base URLs.
- Use the exact current dependency versions recorded in this spec; do not use range specifiers.
- Deliver the initial command surface defined in the command coverage matrix before extending first-class coverage.

### Assumptions

- The executable is named `plane`; the npm package may use a scoped name.
- `PLANE_API_KEY` is the primary PAT environment variable. `PLANE_ACCESS_TOKEN` may be accepted when the selected authentication mode requires a bearer token.
- Profiles persist non-secret context such as base URL, workspace, and default project. Tokens are supplied through the environment in the first release.
- Administrative APIs such as instance administration and IDP group synchronization are not normal project-management operations.
- English is the only interface language in the first release.

## Background

Plane exposes a large REST API covering projects, work items, cycles, modules, initiatives, pages, customers, work item types, releases, workflows, and related resources. Its official Node SDK supplies TypeScript models and resource clients, but its public API is still evolving. Agents need a smaller and more stable command contract than the raw SDK, while human terminal users benefit from an interactive overview and rapid keyboard navigation.

The repository is greenfield. There is no current architecture or compatibility surface.

The exact CLI-to-SDK mapping is maintained in the [command coverage matrix](./2026-08-08-plane-cli-command-matrix.md). Terminal presentation follows the [Plane CLI interface system](../../.interface-design/system.md).

## Decisions

- Decision: Treat deterministic commands as the canonical product interface.
  Source: Confirmed agent-first goal.
  Consequence: TUI components may invoke shared application operations but may not call Plane independently.
- Decision: Open the TUI only for a bare `plane` invocation when stdin and stdout are interactive terminals.
  Source: Confirmed direction.
  Consequence: Scripts and agents cannot enter an interactive session accidentally.
- Decision: Use Plane's official Node SDK behind a narrow adapter.
  Source: Existing official SDK coverage and the requirement to support the public API.
  Consequence: SDK types and errors do not become public CLI contracts, and SDK upgrades can be compatibility-tested centrally.
- Decision: Use regular resource/action command grammar.
  Source: Agent discoverability requirement.
  Consequence: Common actions use `list`, `get`, `create`, `update`, and `delete`; exceptional domain actions use explicit verbs.
- Decision: Keep secrets out of persisted profiles in the first release.
  Source: PAT security requirement.
  Consequence: unattended callers provide credentials through their process environment or secret manager.
- Decision: Provide a raw public-API escape hatch.
  Source: Plane's evolving API and the cost of wrapping every uncommon endpoint immediately.
  Consequence: `plane api` provides coverage without weakening the stability of first-class commands.
- Decision: The first useful release covers context, projects, members, work items, states, labels, comments, cycles, modules, and work-item relations.
  Source: These resources complete the inspect, create, assign, prioritize, schedule, discuss, relate, and close workflow.
  Consequence: Uploads, portfolio resources, custom schemas, releases, workflows, and templates remain available through `plane api` until their first-class commands are implemented.
- Decision: Use one package rather than a monorepo.
  Source: The CLI, TUI, and skill share one release and one operation layer.
  Consequence: Packages may be split only when a separately versioned consumer exists.
- Decision: Use the official SDK first and native `fetch` only for a documented SDK gap.
  Source: Type safety and public API coverage without forking upstream code.
  Consequence: Each direct HTTP exception identifies the missing or defective SDK operation and has a contract test.
- Decision: Keep the first TUI centered on work-item operations.
  Source: Work items are the common unit across Plane workflows.
  Consequence: Less frequent resources remain command-only until a demonstrated human workflow requires a TUI view.

## Scope

### In

- Authentication and connectivity checks.
- Workspace and project context.
- Projects, members, and feature settings.
- Work items, states, labels, comments, activities, attachments, links, relations, dependencies, and worklogs.
- Cycles, modules, epics, initiatives, and milestones.
- Intake, customers, and teamspaces.
- Estimates, work item types, custom properties, and property values.
- Pages, collections, releases, workflows, and templates where present in the public API.
- Human table/plain output, JSON, and JSON Lines.
- Cursor pagination and rate-limit reporting.
- Interactive TUI for navigation, inspection, creation, and editing.
- Agent capability discovery and a packaged Codex-compatible skill.
- Plane Cloud and self-hosted Plane.

### Out

- Plane instance administration, billing, SSO, and IDP synchronization.
- OAuth application registration and interactive browser authentication.
- Webhook hosting or a long-running daemon.
- An embedded natural-language parser or LLM.
- Offline mutation queues or bidirectional synchronization.
- Compatibility aliases for deprecated `issue` commands.
- TUI-only capabilities.
- Standalone native binaries until npm distribution is shown to be insufficient.
- Shell-completion installation in the first release.
- A TUI screen for every command resource.

## Current Architecture

There is no existing application. Plane is the system of record and exposes the only remote integration boundary.

## Target Architecture

```text
process arguments / terminal input
              |
        invocation router
         /            \
 command frontend    TUI frontend
         \            /
       application operations
          |       |
     resolvers   output contracts
          \       /
       Plane SDK adapter
              |
        Plane public API
```

- The invocation router owns TTY detection and selects command or TUI mode.
- Command definitions own names, arguments, options, examples, and machine-readable help metadata.
- Application operations own validation, resource resolution, pagination policy, and destructive-action policy.
- The SDK adapter owns authentication headers, base URL configuration, SDK error normalization, and API-version compatibility.
- Output rendering owns stdout/stderr separation, formats, color policy, and error envelopes.
- The TUI owns terminal layout and input state only.
- The skill consumes public CLI help and behavior; it does not depend on internal modules.

### Repository structure

```text
src/
  cli.ts                 process entry and invocation routing
  commands/              command registration and help metadata
  core/
    client.ts            Plane SDK adapter and direct-HTTP exceptions
    config.ts            environment, profiles, and context
    errors.ts            normalized errors and exit codes
    output.ts            table, plain, JSON, and JSON Lines
    pagination.ts        cursor traversal and rate-limit policy
    resolve.ts           identifiers, UUIDs, names, and `me`
  operations/            resource operations shared by CLI and TUI
  tui/                   Ink application, screens, and components
skills/
  plane-cli/
    SKILL.md
    agents/openai.yaml
```

Do not add per-resource interfaces, dependency-injection containers, plugin systems, or packages without a second concrete implementation or consumer.

## Required Behaviour

### Invocation

- Bare `plane` opens the TUI only when both input and output support interactive terminal behavior.
- Bare `plane` outside a TTY prints machine-readable root help and exits successfully.
- `plane tui` explicitly requests the TUI and fails with a usage error when raw terminal input is unavailable.
- Any resource command remains non-interactive unless it must obtain missing data and `--no-input` was not supplied.
- `--no-input`, `CI`, or non-TTY execution disables every prompt.

### Configuration and authentication

- Configuration precedence is command flags, environment, selected profile, then defaults.
- The default cloud base URL is `https://api.plane.so`.
- A custom base URL must be HTTPS unless the caller explicitly permits insecure HTTP for local development.
- PAT values must never appear in output, logs, error details, shell completion, or persisted profiles.
- `plane doctor` validates configuration and connectivity without mutating Plane.
- Missing, expired, or rejected credentials produce an authentication error with a corrective hint.
- `plane context show`, `list`, `set`, `use`, and `delete` manage named non-secret profiles.
- `plane config path` prints the active configuration file path without creating it.
- Configuration lives in the project-local `.cockpit/config.json` file under the current working directory.
- Configuration writes are atomic and create files with user-only permissions where the platform supports POSIX permissions.

### Resource references

- Commands accept canonical UUIDs.
- Project arguments also accept unique project identifiers.
- Work-item arguments also accept identifiers such as `ENG-142`.
- Commands may accept unique human-readable names where a bounded lookup is available.
- A name matching multiple resources must produce an ambiguity error containing candidate IDs and names. The CLI must not select one implicitly.
- `me` is accepted where the current authenticated user is a valid member reference.

### Commands

- Regular resources expose consistent `list`, `get`, `create`, `update`, and `delete` actions when supported by Plane.
- Domain relationships expose explicit actions, such as adding work items to a cycle or archiving a module.
- Common scalar fields have named flags.
- Complete or uncommon payloads may be supplied with `--data <json>`, `--data @<path>`, or `--data -` for stdin.
- A value supplied both through a named flag and `--data` is rejected rather than merged ambiguously.
- Delete operations require `--yes` when prompts are unavailable.
- Mutating commands return the resulting resource when Plane supplies it, otherwise a stable success result identifying the mutation.
- `plane api <method> <path>` permits authenticated calls only beneath the configured Plane API origin and must reject absolute foreign URLs.

### Output

- `--output table|plain|json|jsonl` selects a format; `--json` and `--jsonl` are shortcuts.
- The default is table output on a TTY and JSON output otherwise.
- Successful machine output is written only to stdout.
- Diagnostics, warnings, and structured failure output are written only to stderr.
- JSON output is UTF-8, contains no ANSI sequences, and has stable top-level envelopes.
- JSON Lines emits one complete object per line and is available only for sequence results.
- Human tables adapt to terminal width and never truncate identifiers.
- `NO_COLOR` and `--no-color` disable ANSI color.

### Pagination and rate limits

- List commands expose `--limit`, `--cursor`, and `--all`.
- Without `--all`, results include Plane's next cursor in machine output and a continuation hint in human output.
- `--all` follows cursors until exhaustion or an explicit limit is reached.
- Rate-limit metadata is retained in machine-readable metadata when available.
- Safe reads may wait for one server-directed rate-limit reset unless the caller disables waiting.
- Mutations are never retried automatically after an ambiguous network failure.

### TUI

- The default view presents work items as flight strips with workspace/project context, filter state, and a persistent key guide.
- The work-item identifier is the strongest stable label; the title is the focal content.
- Terminals at least 100 columns wide use list/detail composition. Narrow terminals use a single navigable pane.
- Keyboard operation covers navigation, filtering, inspection, creation, editing, confirmation, cancellation, and exit.
- Repeated navigation and command-palette interactions have no decorative delay.
- Loading, empty, failure, ambiguous-reference, offline, and rate-limited states state the next valid action.
- TUI colors use terminal capability detection and retain readable hierarchy without color.
- Exiting or crashing restores terminal state.

#### TUI screens and flows

- Startup opens the saved project context. When it is absent or invalid, a searchable workspace/project picker appears before the work-item view.
- The home screen is the flight-strip work-item list. Wide terminals show the selected item's detail pane; narrow terminals open detail as a separate screen.
- `/` opens incremental work-item search without discarding the current selection. Clearing the query restores the previous list and selection.
- `c` opens a create form with name, description, state, priority, assignees, labels, cycle, and module. Only name is required; unresolved optional references remain editable errors rather than being silently dropped.
- `e` opens the same field model populated from the selected work item. Saving sends only changed fields.
- The detail screen exposes comments and relations. Their create/remove actions use the same confirmation and error behavior as commands.
- `:` opens a command palette for actions available in the current context. It does not accept natural language.
- Delete and other irreversible actions open a confirmation showing the exact resource identifier and consequence. The default focused action is cancel.
- A failed mutation keeps the form or confirmation data intact and presents retry/correction actions.
- The TUI does not include pages, releases, workflows, templates, customer management, or administration in the initial release.

### Capability discovery

- Root and command help are available as human text and JSON.
- Machine-readable help includes command path, purpose, arguments, options, accepted input sources, destructive status, and examples.
- `plane doctor --json` reports CLI version, API origin, selected context, authentication status, and supported capability groups without exposing secrets.

### Agent skill

- The packaged skill triggers for Plane project-management requests intended to be performed through the CLI.
- The skill directs agents to run `plane doctor --json` before the first operation in a new environment.
- It requires JSON output, non-interactive mode, explicit pagination, read-before-write behavior, and `--yes` for intentional deletion.
- It documents structured error recovery and several representative workflows.
- It tells agents to query machine-readable help for the current command surface instead of embedding a full reference.
- The skill folder contains `SKILL.md` and `agents/openai.yaml`; it contains no duplicate user documentation.
- The skill contains concise examples for inspecting assigned work, creating a work item, updating state, adding a comment, scheduling into a cycle, relating two work items, handling ambiguity, and continuing pagination.
- The skill defines error recovery by stable CLI error code rather than matching prose.
- The skill forbids guessing resource matches, parsing human tables, retrying ambiguous mutations, and deleting without an explicit user instruction.
- `plane skill path` prints the packaged skill directory. `plane skill install --target <directory>` copies it only to an explicit destination and refuses to overwrite an existing skill without `--force`.

## Contracts

### [ADDED] Command grammar

```text
plane <resource> <action> [reference] [options]
```

Resource names and actions are lowercase kebab-case and singular, for example `work-item get` and `work-log create`.

### [ADDED] Success envelope

```json
{
  "schemaVersion": 1,
  "data": {},
  "meta": {
    "requestId": "optional",
    "nextCursor": "optional",
    "totalResults": 1,
    "rateLimitRemaining": 59,
    "rateLimitReset": "optional ISO-8601 timestamp"
  }
}
```

`data` may be an object, array, scalar, or `null`. Unavailable metadata keys are omitted.

### [ADDED] Error envelope

```json
{
  "schemaVersion": 1,
  "error": {
    "code": "ambiguous_reference",
    "message": "Project name matches more than one project.",
    "status": 409,
    "hint": "Use a project identifier or UUID.",
    "details": {
      "candidates": []
    },
    "requestId": "optional"
  }
}
```

Stable error codes include `usage`, `authentication`, `authorization`, `not_found`, `ambiguous_reference`, `validation`, `conflict`, `rate_limited`, `network`, and `server`.

JSON Lines output emits one `{ "schemaVersion": 1, "data": ... }` object per line. Empty sequences emit no lines.

### [ADDED] Exit codes

| Code | Meaning |
| ---: | --- |
| 0 | Success |
| 1 | Unclassified runtime or server failure |
| 2 | Usage or local validation failure |
| 3 | Authentication or authorization failure |
| 4 | Missing or ambiguous resource |
| 5 | Conflict or rejected mutation |
| 6 | Rate limit not recovered |
| 7 | Network unavailable or timed out |

### [ADDED] Configuration inputs

| Setting | Flag | Environment | Profile |
| --- | --- | --- | --- |
| Base URL | `--base-url` | `PLANE_BASE_URL` | Yes |
| API key/PAT | `--api-key-stdin` | `PLANE_API_KEY` | No |
| Access token | `--access-token-stdin` | `PLANE_ACCESS_TOKEN` | No |
| Workspace | `--workspace` | `PLANE_WORKSPACE_SLUG` | Yes |
| Project | `--project` | `PLANE_PROJECT` | Yes |
| Profile | `--profile` | `PLANE_PROFILE` | N/A |

Secrets are not accepted as ordinary command arguments because process listings and shell history may expose them.

### [ADDED] Machine-readable help

```json
{
  "command": "work-item update",
  "description": "Update a work item.",
  "destructive": false,
  "arguments": [],
  "options": [],
  "examples": []
}
```

### [ADDED] Public operation boundary

Application operations accept validated command input and return domain data or normalized errors. Neither command output nor TUI state exposes SDK-specific error classes or Axios response objects.

### [ADDED] SDK fallback boundary

- The SDK adapter is the default transport for every operation it supports correctly.
- A direct HTTP implementation may be added only when the pinned SDK lacks the endpoint or fails its documented contract.
- Direct HTTP calls use native `fetch`, the same authentication/configuration/error normalization, and only paths beneath the configured API origin.
- Each exception records the affected SDK version and an upstream issue or concise compatibility note in code.
- Do not fork, patch in `node_modules`, or expose SDK response/error objects.
- `plane api` always uses the direct HTTP path because it is explicitly an escape hatch.

## Deletion Criteria

- The raw `plane api` path may be removed for a resource only when every public operation for that resource has a stable first-class command and no supported self-hosted version requires the escape hatch.
- Any temporary SDK compatibility mapping may be removed after the minimum supported SDK version exposes the normalized behavior and its compatibility contract passes against Plane Cloud and the oldest supported self-hosted release.

## Acceptance Criteria

- [ ] Bare `plane` opens the TUI in an interactive terminal and never opens it in a pipe or CI process.
- [ ] An agent can discover, create, inspect, update, relate, comment on, and close a work item using only JSON help and command output.
- [ ] Every TUI mutation has an equivalent documented command.
- [ ] JSON and JSON Lines output contain no prose, spinners, ANSI escapes, or prompts.
- [ ] Authentication supports Plane Cloud and a configured self-hosted base URL without persisting tokens.
- [ ] Project identifiers and work-item identifiers resolve correctly; ambiguous names fail with candidates.
- [ ] Cursor pagination can be resumed and `--all` terminates at exhaustion or its limit.
- [ ] Destructive non-interactive operations fail unless `--yes` is present.
- [ ] PATs are redacted from debug output and all normalized errors.
- [ ] The CLI exposes first-class commands for every in-scope resource group and `plane api` covers public API gaps.
- [ ] Rate-limited reads recover according to server metadata; mutations are not retried after ambiguous failures.
- [ ] The TUI renders useful loading, empty, error, and narrow-terminal states and restores terminal state on exit.
- [ ] The packaged skill passes structural validation and enables a fresh agent to complete the representative work-item workflow.
- [ ] Type checking, command contract tests, TUI snapshot tests, and live sandbox smoke tests pass.
- [ ] Every initial-surface command in the coverage matrix is implemented and tested through its public executable contract.
- [ ] Dependencies match the exact baseline versions and the package declares Node `>=22.12.0`.

## Testing Strategy

- Unit-test configuration precedence, reference parsing, payload-source exclusivity, TTY routing, exit-code mapping, redaction, and pagination termination.
- Contract-test every command's JSON success, JSON error, JSON Lines, and machine-help shapes through the executable interface.
- Test application operations against fake SDK resource methods for success, Plane validation failures, ambiguity, rate limits, and network uncertainty.
- Snapshot-test TUI states at wide and narrow widths with color enabled and disabled.
- Run integration tests against a dedicated Plane sandbox for authentication, project lookup, work-item lifecycle, relationships, comments, pagination, and cleanup.
- Gate destructive sandbox tests behind an explicit environment setting and use uniquely prefixed disposable resources.
- Forward-test the packaged skill with a fresh agent using only the installed CLI, the skill, and sandbox credentials.
- Visually inspect at least one light terminal, one dark terminal, a 256-color terminal, and a narrow terminal because terminal rendering cannot be fully verified through snapshots.

## Operational Considerations

- Treat credentials and Plane content as sensitive. Telemetry is disabled by default and no command payloads are collected.
- Debug logging redacts authorization headers, credential-shaped values, and request bodies unless the caller explicitly requests body logging; body logging remains off by default.
- Release notes identify the minimum supported Plane Cloud/API behavior and tested self-hosted Plane versions.
- Exact SDK versions are pinned. Upgrades require command-contract and live sandbox verification.
- Rate-limit behavior must honor Plane response headers and avoid request bursts from `--all` or the TUI.
- The CLI identifies its version in the HTTP user agent to support server-side diagnosis.
